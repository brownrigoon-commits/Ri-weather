# 위성 홀 매칭 설계 초안 — 골프존 이미지의 자체 대체 (2026-07-29, 클라우드 세션)

"골프존 데이터를 가지고 위성사진의 홀별 사진을 매칭하여 캐디 공략에 적용.

## 1. 반드시 기억할 실패 이력

`js/holesdb.js` 주석에 남아 있다: 예전에 위성사진만 보고 홀 위치를 '추정'한 데이터가 있었고,
**홀 번호·경로가 실제와 달라 전량 제거했다** (신뢰 우선 원칙).

이번이 그때와 다른 결정적 차이 — **골프존 수치가 자동 검증 정답지로 있다.**
그때는 추정이 맞는지 확인할 방법이 없었지만, 지금은 홀 수·파·티별 거리·고도차라는
기계 판정 가능한 기준이 있다. **검증을 통과한 구장만 전환한다**는 관문이 이 설계의 심장이다.

## 2. 재료 (전부 이미 보유)

| 재료 | 어디에 | 역할 |
|---|---|---|
| 구장 위치 | `js/golfdb.js` (lat/lon) | 위성 타일 범위 |
| 위성 타일 | Esri World_Imagery (앱이 이미 사용, legal.js 출처 표기됨) | 이미지 원판 |
| OSM 골프 데이터 | Overpass `golf=hole|tee|green|fairway|bunker` | 일부 구장은 홀 라인이 이미 공개돼 있음 — 가장 쉬운 출발점 |
| 골프존 홀맵·수치 | `coursedata/homepages/gz*/parsed.json` | **매칭 참고 + 검증 정답지** (산출물에는 안 들어감 — 5장) |
| 세로 홀 뷰 렌더러 | `renderHoleCanvas()` | 좌표 → 화면 (완성품) |
| 수집 인프라 | `tools/collect_v2_selenium.py` 등 | 배치 처리 골격 재활용 |

## 3. 파이프라인 (구장 단위)

```
1. 후보 수집   : OSM 홀 라인 조회 → 있으면 그대로 후보
                 없으면 위성 이미지에서 페어웨이·그린 검출로 티·그린 후보 생성
                 (색·형태 분석, 필요 시 비전 AI에 위성사진+골프존 홀맵을 주고 대응을 묻는 방식 병행)
2. 번호 매칭   : 골프존 홀맵의 모양·파·거리와 후보 라인 대조 → 홀 번호 배정
3. 자동 검증   : (관문 — 4장 기준) 통과 못 하면 그 구장은 전환 보류
4. 산출       : coursedata/satlines/<구장>/lines.json (홀별 line·par·번호)
5. 조립       : holeimgdb 항목을 line 기반으로 교체(또는 HOLES_DB 부활) → 위성 홀 뷰 + 샷별 캐디
6. 삭제       : 전환 확정 구장의 gz 이미지 폴더 제거 (리스크 버튼 로직 재사용)
```

## 4. 자동 검증 관문 (전환 여부를 기계가 판정)

절대 원칙 1(홀 하나라도 빠지면 등록 금지)·2(틀릴 수 있으면 표시하지 않음)를 그대로 적용한다.

| 검사 | 기준(초안 — 파일럿에서 확정) |
|---|---|
| 홀 수 | 골프존 홀 수와 정확히 일치. 하나라도 못 찾으면 **구장 전체 보류** |
| 홀 길이 | 라인 길이 vs 골프존 최장 티 거리, 오차 허용치 이내 (초안 ±8% — 파일럿에서 조정) |
| 파 정합 | 라인 길이가 그 홀 파의 통상 대역과 일치 |
| 방향 | 티→그린 방향이 인접 홀 배치와 모순 없음 (9홀 순환 구조) |
| 사람 표본 | 구장당 무작위 2홀을 골프존 홀맵과 눈으로 대조 (전수 아님 — 표본) |

- **전 홀 통과 구장만 전환.** 부분 통과 구장은 골프존 이미지를 유지한 채 다음 라운드로
  (한 번에 다 안 돼도 된다 — 통과분부터 순차 전환하면 리스크가 그만큼씩 줄어든다).
- 검증 스크립트를 만들면 **일부러 홀 하나를 비틀어 넣어 검사가 잡는지 확인 후 원복** (저장소 규칙).

## 5. 법리 관점 — 왜 이 방식이 안전해지는가

- 산출물(홀 좌표 + 위성 렌더링)에는 **골프존 콘텐츠가 한 조각도 들어가지 않는다.**
  실제 지형 위 홀의 배치는 저작물이 아니라 **사실**이고, 위성 이미지는 Esri 약관에 따라
  출처 표기로 사용 중인 별개 소스다.
- 골프존 홀맵을 제작 과정에서 **대조·검증용으로 참고**하는 것은 복제물을 서빙하는 것과
  차원이 다른 낮은 위험이다 (사실 확인용 참조).
- 산출 lines.json에 골프존 유래 표기·문구를 넣지 않는다. 골프존 공략 TIP 문구도 옮기지 않는다
  (그 자리는 샷별 AI 캐디가 대신한다).
- Esri 타일 출처 표기는 legal.js에 이미 있음 — 위성 홀 뷰 화면에도 출처 줄 유지.

## 6. 단계 계획

| 단계 | 내용 | 판정 |
|---|---|---|
| 파일럿 | OSM 홀 라인이 있는 구장 5곳으로 파이프라인 전체 가동 | 검증 통과율·오차 분포 측정 → 허용치 확정 |
| 1차 배치 | OSM 라인 보유 구장 전체 | 통과분 전환·배포 |
| 2차 배치 | OSM 없는 구장 — 위성 검출·비전 AI 매칭 | 여기가 난제. 파일럿 결과 보고 방법 확정 |
| 마무리 | 전환 구장 gz 이미지 삭제(백업 후 — 리스크 버튼 절차), 잔여 구장 목록 보고 | 잔여분은 유지 or 준비중 전환을 사장님 결정 |

정직한 예상: **전 구장 자동 전환은 어려울 수 있다.** OSM 데이터가 없는 산악 구장,
숲에 가린 홀 등은 검증을 통과하지 못할 것이다. 그래도 통과하는 구장 수만큼
리스크가 계단식으로 줄고, 남는 구장은 그때 가서 (골프존 유지 / 준비중 강등 / 수동 보정) 결정하면 된다.

## 7. 이 작업으로도 안 없어지는 것 (정직 표기)

| 항목 | 상태 | 처리 방향 |
|---|---|---|
| 3D영상 핫링크 3,834개 | 저장 안 하므로 위험 낮음, 그러나 잔존 | 사장님 표현대로 "영상만 해결하면 끝" — 제거 or 유지(차단당하면 자동 숨김)를 전환 완료 시점에 결정 |
| 티별 거리·파 수치 | DB권 쟁점 잔존 (이미지보다 한 단계 낮은 위험) | **자체 라인 실측 길이로 홀 길이를 대체**하고, 티별 거리는 골프장 스코어카드 재수집으로 점진 교체 가능 — 2차 과제 |
| 고도차(elev) | 위와 동일 | 공개 지형 데이터(DEM)로 자체 산출 가능 — 2차 과제 |

## 8. 오퍼스5 착수 순서 (③ 차례가 왔을 때)

1. 파일럿 5구장 선정 (OSM 라인 보유 + 골프존 등록 교집합 스크립트로 뽑기)
2. 매칭·검증 스크립트(`tools/satmatch_build.py`·`tools/satmatch_verify.py` 가칭) — 검증부터 만들고 일부러 고장 내서 확인
3. 파일럿 결과표(통과율·오차 분포)를 사장님 보고 → 허용치·2차 배치 방법 확정
4. 통과 구장 전환 배포(표준 관문) → gz 이미지 백업 후 삭제
5. 잔여 구장 목록 + 영상·수치 처리안 보고
