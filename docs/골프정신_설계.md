### 명언 선택 로직 — 서버 없이 결정적으로

```js
function todayQuote() {
  const now = new Date();
  const day = Math.floor((now - new Date(now.getFullYear(), 0, 0)) / 86400000);  // 1~366
  return QUOTES_DB[day % QUOTES_DB.length];
}
```
- 모든 유저가 같은 날 같은 명언을 본다(라운드 대화 소재가 되는 부수 효과).

**그룹 ② 아마추어 필드 룰** — 동호회·친선 라운드에서 실제로 통용되는 약속들.
원자료는 사장님 제공 동호회 필드 룰 전문(2026-07-31, 부록 C). **절대 원칙: 정식 규칙과 다른
항목은 카드 안에 반드시 "정식 규칙에서는 ~" 병기** — 앱이 필드 룰을 정식 룰로 오해시키면
룰 코너 전체의 신뢰가 무너진다. 톤은 "이렇게들 합니다"(관행 소개)이지 "이렇게 하세요"(규정)가 아니다.

| 카드 | 요지 (정식 규칙과의 차이 병기) |
|---|---|
| 시작 전 합의가 최고의 룰 | 필드 룰의 제1원칙 — 애매한 건 시작 전에 정하고, 라운드 중엔 정한 대로. 전원이 합의하면 그 라운드의 룰이 된다. 이 그룹의 모든 카드가 이 전제 위에 있다 |
| 멀리건은 없다 | 대회는 물론 정식 라운드에도 멀리건은 없다. 친선에서 첫 티샷 한 번 정도를 합의로 허용하는 문화가 있을 뿐 |
| OK(기브)는 몇 미터? | 아마추어는 진행을 위해 퍼터 길이(약 1m) 안쪽을 OK로 주는 문화. **정식 스트로크플레이에는 OK가 없다**(매치플레이 컨시드만). 기준과 '누가 주는지'(조장 등)를 시작 전에 정하면 다툼이 없다 |
| 볼 수색은 짧게 | **정식은 3분**이지만 동호회는 진행을 위해 1분으로 줄여 합의하기도 한다. 짧게 정할수록 뒷팀이 편하다 |
| 티샷 OB → 특설티 | 정식(스트로크와 거리)대로면 티박스에서 3타째. 국내 구장 대부분은 특설티(OB티)를 운영 — 특설티로 가면 보통 +2벌타로 다음 샷이 4타째. **구장 로컬룰 안내가 우선** |
| 페널티구역 → 특설티 | 정식은 규칙 17의 구제 선택지(1벌타). 아마추어 라운드에선 특설티(+1벌타 3타째)나 경계 통과 선상 두 클럽 드롭으로 단순화하는 문화 |
| 세컨샷 OB를 그 자리 드롭으로 | **정식은 친 자리로 돌아가 다시**(스트로크와 거리). 진행을 위해 나간 지점 부근 +1벌타 드롭으로 완화하기도 — 정식 룰이 아님을 알고 쓰자 |
| 디봇 속 볼 | **정식 규칙엔 구제가 없다**(놓인 그대로 친다). 아마추어 합의로 한 뼘 옆 무벌타 이동을 허용하기도 — 옮길 땐 동반자에게 먼저 알리는 것이 매너 |
| 벙커 발자국 속 볼 | **정식 구제는 없다.** 정리 안 된 발자국은 앞 팀의 매너 문제라, 동호회에선 무벌타 옆 드롭을 합의하기도 한다. 나부터 발자국을 고르게 정리하자 |
| 니어리스트·롱기스트 | 대회 이벤트 상: 니어리스트는 그 홀 파 이상, 롱기스트는 페어웨이 안착+파 조건이 일반적. 조건과 측정 담당은 대회마다 다르니 시작 전 확인 |
| 조장은 그 조의 심판 | 동호회 라운드에서 OK 부여·거리 체크·애매한 판정은 조장 몫. 조장 판정에 따르는 것이 필드 룰의 기본 |
| 내기는 금지가 기본 | 동호회 대부분이 내기를 금지하거나 '자기 책임'으로 둔다. 조인 매너 탭의 원칙과 같다 |

## 7. 세계 골프 룰 — 매월 자동 점검 설계 (감지·알림·기록 자동, 반영은 검토 후)

### 사실부터 (조사 결과, 출처는 부록 C)

- 규칙 본문은 **4년마다** 개정. 현행 2023년판, **차기 2027년 1월 예상(공식 미발표)**.
- 그 사이 **분기별**(1·4·7·10월) Clarifications(유권해석). 최신판 2026-07-01자 확인.
- KGA 가 한글 번역 Clarifications 를 무료 게시(로그인 불필요, 실제 PDF 확인).
- R&A 자료 허브는 정적 HTML 에 "updated 1 July 2026" 식 날짜가 있어 **파싱으로 감지 가능**
  (URL 은 부록 C). USGA 페이지는 봇 차단(403). RSS 는 세 기관 모두 없음.

### 구조

```
매월 2일 09:00 KST — .github/workflows/golfrules.yml (cron "0 0 2 * *" ← GitHub cron 은 UTC!)
  └─ tools/check_golfrules.py
       ① R&A rules-resources 에서 Clarifications 날짜 추출
       ② KGA 골프규칙소식 게시판 최신 글 제목 추출
       ③ coursedata/workfiles/golfrules_snapshot.json 과 비교
       ├─ 변경 없음 → 스냅샷의 lastChecked 갱신을 **커밋**(contents:write, ristock 선례)
       │              — 이 월 1회 소커밋이 ⓐ 화면의 "최근 점검" 근거가 되고
       │                ⓑ 스케줄 워크플로 60일 비활성화도 막아준다
       ├─ 변경 감지 → 리포트 docs/골프룰_점검리포트.md 생성·커밋 후 **exit 1 (워크플로 실패)**
       │              — GitHub 이 실패를 소유자 메일로 알린다. 조용한 성공으로 위장하지 않는다
       └─ 페이지 접속 실패 → 마찬가지로 exit 1 — **침묵은 성공이 아니다**
```

- **화면 표시**: 룰 탭이 `golfrules_snapshot.json` 을 fetch 해 "최근 점검 {lastChecked}" 를,
  `SPIRIT_DB.updated` 로 "내용 반영 {updated}" 를 **분리 표시**한다(fetch 실패 시 반영일만).
  이 구조라야 '점검이 멈춤'과 '변경 없음 지속'을 화면에서 구분할 수 있다.
- **반영 절차**(변경 감지 후): 다음 작업 세션에서 리포트 확인 → KGA 한글 Clarification 원문
  대조 → 카드 영향 판단 → SPIRIT_DB 수정 + updated 갱신 → sweep → 배포 → HANDOFF 기록.
- **왜 마지막 반영은 사람(클로드) 검토를 거치나** — 규칙을 자신 있게 틀리게 적는 것이 최악이다
  (초안 검증에서도 룰 카드 14개 중 1개의 오류가 사람 검증으로 잡혔다). Clarifications 는 미묘한
  해석이라 기계 치환이 불가능하고, 분기 1회 이하라 검토 비용도 작다. 사장님 지시의 "수정까지"는
  '감지 → 리포트 → 수정 → 배포'가 한 파이프라인으로 이어진다는 뜻으로 구현하되,
  수정 문장을 쓰는 한 걸음만 검토를 거친다 — 며칠의 지연과 정확성을 맞바꾼 것이다.
